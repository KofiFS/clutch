# Clutch architecture review

**Clutch has a credible foundation for a local-first Medal alternative. It is ready to compete on local ownership and straightforward editing, but replay reliability, default save latency, and consent defaults need work before I’d recommend it as someone’s only recorder.** Keep FFmpeg and Electron for now. The highest-value changes are to make each save durable, isolate capture from UI failures, and make the shipped defaults match the product promise.

This is a static review of the checkout. I did not run either recorder, benchmark a game, or modify files. Competitor documentation establishes features and advertised behavior. FPS cost, memory, and failure rates remain unmeasured.

## Architecture as shipped

| Area | Implementation |
|---|---|
| Processes and IPC | Electron main owns the recorder, hotkeys, tray, library, upload scheduler, updater, and media protocol. React runs the main UI and mini widget. The preload exposes typed `window.cf` commands and event subscriptions. The main renderer stays available for system-audio loopback, with background throttling disabled. [Main window and lifecycle](../../src/main/index.ts:62) · [Preload bridge](../../src/preload/index.ts:28) · [Renderer audio lifecycle](../../src/renderer/src/lib/store.tsx:122) |
| Capture | One FFmpeg process captures a window with Windows Graphics Capture or a monitor/region with DXGI Desktop Duplication. DirectShow supplies microphones, Chromium’s loopback supplies desktop PCM through IPC and stdin, and PowerShell helpers supply per-app PCM over named pipes. FFmpeg encodes a rolling set of two-second MPEG-TS files. Clip saves concatenate and stream-copy selected segments into MP4. Long recordings pin segments and support bookmarks. | Storage | Clips are ordinary MP4s under the chosen output directory. Settings, native and external clip indexes, thumbnails, and the replay buffer live separately. External libraries, including Medal folders, are indexed in place. A custom `cf://` protocol serves local media with byte ranges. ## Head-to-head with Medal

| What gamers notice | Assessment |
|---|---|
| **Capture and in-game FPS** | **Competitive path on NVIDIA. Higher overhead risk on AMD, Intel, and scaled capture.** At native resolution, NVENC can consume D3D frames directly. The other path downloads frames to system memory and converts them before encoding, even with AMF or QSV. CPU fallback adds x264 encoding. Medal offers GPU and CPU encoding and documents contention under GPU saturation. There is no basis here for a relative FPS number. [Clutch capture path](../../src/main/capture/replayBuffer.ts:349) · [Frame transfers](../../src/main/capture/replayBuffer.ts:397) · [Medal performance guide](https://support.medal.tv/support/solutions/articles/48000922094) |
| **Replay reliability** | **Clutch has concrete failure modes that prevent a parity claim.** Two-second disk segments, a stall watchdog, and restart backoff are sound building blocks. Ordinary restarts can discard the buffer, and a spawned process can appear ready before it has written usable footage. Medal also documents capture failures. Neither product’s failure rate is established here. [Buffer lifecycle](../../src/main/capture/replayBuffer.ts:106) · [Restart handling](../../src/main/recorder.ts:630) · [Medal troubleshooting](https://support.medal.tv/support/solutions/articles/48000922120/create_ticket) |
| **Clip latency** | **Worse default for a player who wants the moment immediately.** Clutch’s default hotkey includes five seconds after the press, then waits another 2.75 seconds before remuxing. The library entry and “Clipped!” feedback follow probing and thumbnail generation. Stream copy keeps the export itself cheap, but the default path has about **7.75 seconds of scheduled wait** before that work. Medal documents a retrospective hotkey workflow. Its actual save latency is unmeasured here. [Clutch defaults](../../src/shared/types.ts:496) · [Save timing](../../src/main/capture/replayBuffer.ts:548) · [Library insertion](../../src/main/library/index.ts:251) · [Medal clip capture](https://support.medal.tv/support/solutions/articles/48001157616) |
| **Audio tracks** | **Near parity at capture, behind in editing.** Clutch can write a playback mix first and named mic/app tracks after it, useful for keeping Discord editable in another tool. Its built-in reframe and join paths use the first audio stream. Medal exposes detached tracks on its timeline with per-track adjustment. Clutch’s desktop PCM also depends on a live renderer. [Clutch audio graph](../../src/main/capture/replayBuffer.ts:408) · [Editor stream selection](../../src/main/editorArgs.ts:57) · [Medal multitrack](https://support.medal.tv/support/solutions/articles/48001220541/) |
| **Game detection** | **Behind for automatic coverage, with useful manual controls.** Clutch has a game picker, per-game profiles, and background discovery. Its classifier relies on user lists, executable paths, and fullscreen state. Foreground polling runs every three seconds, with a separate 15-second scan. That can miss early footage or misclassify a fullscreen app. Medal documents a supported-game catalog and a manual add flow. [Clutch classifier](../../src/main/capture/foreground.ts:176) · [Polling](../../src/main/recorder.ts:215) · [Medal supported games](https://support.medal.tv/support/solutions/articles/48000971430/) |
| **Editor** | **Competitive for basic creator workflows, behind for timeline editing.** Clutch offers trim, reframe for vertical or square, speed, joins, and on-device caption generation. Medal’s advanced timeline, montage tools, and track controls are broader. [Clutch editor](../../src/main/editor.ts:30) · [Medal advanced editor](https://support.medal.tv/support/solutions/articles/48001275437-video-editor) · [Medal montage](https://support.medal.tv/support/solutions/articles/48001185258/) |
| **Sharing** | **Better fit for local files and direct publishing, behind for a social workflow.** Clutch gives users ordinary files plus Discord webhooks, YouTube scheduling, and optional hosted links. Medal offers local storage and optional auto-upload too, alongside albums, social discovery, and cross-device cloud workflows. Clutch’s advantage is the account-free local workflow, and the backup default weakens that advantage once a user signs in. [Clutch sharing](../../src/main/index.ts:248) · [Medal settings](https://support.medal.tv/support/solutions/articles/48001271487/) · [Medal Cloud](https://support.medal.tv/support/solutions/articles/48001258314/) |
| **Library at thousands of clips** | **Clutch has a clear scaling limit.** In-place folder indexing is good for migration. Queries synchronously check file existence, filter and sort in main, then send the full result to a non-virtualized React grid. Medal documents richer filters and bulk operations. Its throughput at the same clip count is unknown. [Clutch query](../../src/main/library/index.ts:230) · [Grid rendering](../../src/renderer/src/pages/Library.tsx:235) · [Medal library](https://support.medal.tv/support/solutions/articles/48001164598-how-to-manage-clips-on-medal) |
| **Startup and memory** | **Unproven against Medal.** Clutch pays for Electron/Chromium, FFmpeg, and hardware-dependent helper processes. It loads JSON indexes synchronously before the window and runs serial encoder probes on the first uncached check. A quick window launch could still hide a slow time to first usable replay. The included benchmark samples process CPU and memory plus NVIDIA utilization, but cannot answer cold-start time or game frame-time cost. Clutch’s voice, hype, and optional visual triggers are useful across games, but they provide different coverage from explicit match and event data. ## Ranked weaknesses and risks

1. **Critical — Consent defaults contradict the promise.** `showAds` defaults to `true`. Home and Library mount sponsored cards, and the server counts impressions and clicks. `backupFavorites` also defaults to `true`. A signed-in Pro user can have favorites uploaded through the same path as manual sharing, creating a link that serves media to anyone holding it. Unshare swallows server errors and clears local cloud metadata anyway. [Defaults](../../src/shared/types.ts:567) · [Sponsored card](../../src/renderer/src/components/Account.tsx:179) · [Ad counters](../../server/src/index.mjs:265) · [Backup job](../../src/main/index.ts:267) · [Unshare](../../src/main/index.ts:480) · [Public media](../../server/src/index.mjs:167)
2. **Critical — A replay can disappear or be overwritten.** Stall recovery and capture-setting changes use starts that can clear the segment directory, including footage held for a pending save. Save ranges use file creation times and an assumed segment duration, which can drift from the media timeline. Manual saves can overlap, and their destination names have second-level precision with FFmpeg overwrite enabled. Two requests can target the same file. [Restart cleanup](../../src/main/capture/replayBuffer.ts:106) · [Settings restart](../../src/main/recorder.ts:187) · [Stall recovery](../../src/main/recorder.ts:642) · [Segment timing and export](../../src/main/capture/replayBuffer.ts:475) · [Clip naming](../../src/main/recorder.ts:821)
3. **High — Recording status can hide missing footage or audio.** The app reports running on spawn. The watchdog sees segment-number progress, so it can miss duplicated or frozen frames that keep getting muxed. Renderer loopback loss becomes silence. The PCM pumps ignore stream backpressure, and stopping with desktop audio kills FFmpeg because stdin carries PCM, leaving a tail that must be probed and may be discarded. [Spawn and status](../../src/main/capture/replayBuffer.ts:151) · [Watchdog](../../src/main/capture/replayBuffer.ts:495) · [Desktop PCM pump](../../src/main/capture/replayBuffer.ts:263) · [App PCM pump](../../src/main/capture/appAudio.ts:100) · [Stop and tail handling](../../src/main/capture/replayBuffer.ts:203)
4. **High — The local catalog can block capture control and lose metadata.** Queries do synchronous filesystem work on Electron main. Mutations rewrite whole JSON files in place, so interruption during a write can lose titles, tags, and catalog state even if the MP4 survives. The renderer mounts every matching card. This makes a large library a recorder concern as well as a UI concern. [Index read/write](../../src/main/library/index.ts:62) · [Query](../../src/main/library/index.ts:230) · [Grid](../../src/renderer/src/pages/Library.tsx:235)
5. **High — Local ownership defaults can delete recordings or replace originals.** The default 100 GB limit permanently removes older non-favorites after trash. Automatic shrinking can replace eligible originals with a re-encoded file. Both are defensible storage features, but they need clear consent given Clutch’s promise. Game-window capture can also fall back to monitor pixels, broadening what can appear in a clip. [Storage defaults](../../src/shared/types.ts:575) · [Janitor](../../src/main/library/janitor.ts:52) · [Replacement](../../src/main/library/compressor.ts:118) · [Capture fallback](../../src/main/recorder.ts:287)
6. **Medium-high — Privileged desktop boundaries are too broad for a recorder that handles private media.** The main renderer disables sandboxing, the media scheme bypasses CSP, and its allowed roots include all of `userData`. Several IPC handlers accept renderer input directly. The bridge should expose the specific actions and files each window needs, with sender and payload validation at the main-process boundary. [Scheme and window](../../src/main/index.ts:37) · [Media roots](../../src/main/index.ts:290) · [IPC handlers](../../src/main/index.ts:575)
7. **Medium — Performance and release inputs vary across machines and builds.** Encoder probes use a tiny synthetic input, which does little to establish that the chosen GPU path works with the actual capture device, scale, and game load. The FFmpeg download tracks a moving release asset, and signing can be omitted. These make regressions harder to reproduce and attribute. [Encoder probing](../../src/main/capture/ffmpeg.ts:60) · [FFmpeg download](../../scripts/fetch-ffmpeg.ps1:48) · [Signing](../../scripts/dist.mjs:16)

## Prioritized improvement plan

Effort estimates assume one developer familiar with the repo.

| Priority | Change | Expected impact | Effort |
|---|---|---|---|
| **P0 · Quick win** | Default ads and favorite backup to off. Separate private backup from link creation and retain the cloud record when revocation fails. Make permanent auto-deletion, replacement of originals, and monitor fallback explicit choices. Migrate old defaults where user intent can be determined. | Aligns shipped behavior with the ownership promise and reduces surprise uploads, capture, and deletion. | **2–4 days** for defaults, migration, and UI. Private backup needs a separate server change. |
| **P0 · Quick win** | Give saves unique job and destination IDs. Write to a temporary file, validate it, and publish by rename. Acknowledge hotkeys immediately, then signal when the clip is playable. Offer zero post-roll as the default for retrospective hotkeys. Wait for the needed segment to close instead of adding a fixed 2.75-second delay. | Removes filename collisions and partial final files. Reduces perceived and actual save latency. | **3–5 days** |
| **P0 · Refactor** | Give capture sessions distinct generations and maintain a manifest of closed segments with media timestamps and stream layouts. Preserve pinned segments across restarts, recover completed segments after a crash, and handle gaps and codec changes explicitly. Derive readiness from usable media. | Makes replay saves predictable across alt-tab, game exit, device changes, and concurrent hotkeys. | **2–4 weeks** |
| **P1 · Quick win** | Extend the benchmark with cold launch to first playable replay, hotkey to playable MP4, dropped or duplicated frames, A/V drift, disk writes, and private memory. Compare each product against a no-recorder baseline at matched output settings on NVIDIA, AMD, and Intel. Record game frame times and 1% lows. Pin FFmpeg by version and hash and require signing for public releases. | Gives Clutch a defensible performance comparison and repeatable regression checks. | **4–7 days** for tooling and first runs, plus hardware coverage. |
| **P1 · Refactor** | Put desktop loopback and recorder supervision in a capture worker. Add bounded queues, clocked PCM, audio-source health, and a graceful control channel independent of PCM. Use benchmark results to target GPU-resident scaling and AMF/QSV interop. | Recording survives renderer failures. Audio gaps become visible, and scaled or non-NVIDIA configurations get a path to lower overhead. | **3–6 weeks**, across audio and GPU work. |
| **P1 · Refactor** | Move local metadata to SQLite in a worker, migrate existing JSON, and page indexed queries over IPC. Virtualize the grid and move probing and thumbnails off the clip-ready path. Validate with a 10,000-clip library and disconnected external folders. | Faster browsing and startup, less interference with capture, and durable metadata. | **2–3 weeks** |
| **P1/P2 · Targeted work** | Narrow the media and IPC boundaries. Then improve game identification with a small maintained executable catalog and window/process events, and preserve or remix isolated audio in editor exports. | Protects private media and closes two visible gaps for Medal switchers. | **3–5 days** for the first security pass, **1–2 weeks each** for detection and editor audio. |

The first release gate I’d set is simple: a hotkey-confirmed clip survives a recorder restart, becomes playable promptly, and stays local unless the user explicitly chooses to send it somewhere. That will do more for Clutch’s competitiveness than another editor effect or trigger.
