# Renderer can launch arbitrary files or programs via shell.openPath using settings:set-controlled library and clips-folder paths

**ID:** vuln-0013
**Severity:** MEDIUM
**Found:** 2026-11-19 17:11:37 UTC
**Target:** Clutch desktop app (src/main/index.ts)
**CWE:** CWE-73
**CVSS:** 6.4
**Confidence:** Medium
**Fix Effort:** Low

## Description

The `libraries:open` and `library:openFolder` IPC handlers pass a path read from the settings straight to `shell.openPath`. The settings are writable by the renderer through the unvalidated `settings:set` channel, so a compromised renderer can point the path at an executable or a network share file and have the main process launch it. This reopens the program-launch risk that the earlier review closed for `system:openExternal`.

## Evidence

Output of the PoC against the unmodified handlers:

```text
shell.openPath calls: [["shell.openPath","/bin/sh"],["shell.openPath","/bin/ls"]]
```

Output after adding the directory check to both handlers:

```text
shell.openPath calls: []
```

and a legitimate library directory still reached `shell.openPath` in the patched run.

## Impact

A script running in the renderer can make the main process open any existing file or UNC path with its default Windows handler, which runs executables (.exe, .bat, .lnk, .hta, .msi and similar). With a payload at a UNC path or one the attacker can drop locally, this gives code execution as the user, and it also forces an SMB connection to an attacker host. It defeats the stated goal of the `isSafeExternalUrl` hardening, which was to stop injected UI script from launching programs. The harness demonstrates the unchecked call; the actual process launch on Windows was not executed.

## Counterevidence

No validation exists between `settings:set` and the two `shell.openPath` calls; `isSafeExternalUrl` and `lockWindow` only guard `openExternal` and navigation, not `openPath`. Mitigating factors: a renderer compromise is required first (sandbox, contextIsolation and navigation lock are on), `openPath` takes no command-line arguments, and Windows may show a warning for executables on remote shares.

## Confidence Rationale

The unchecked data flow from the IPC channel to `shell.openPath` was run against the real handlers, but the final launch of a program by ShellExecute on Windows could not be executed in the Linux sandbox.

## What Would Change This Severity

A demonstrated renderer foothold reachable from remote content, or proof that a payload file can be placed at a local path without user action, would raise this to high; proof that Windows always blocks the launched file would lower it to low.

## Technical Analysis

`settings:set` merges any renderer patch into the stored settings (src/main/index.ts:440; `SettingsStore.set` uses `deepMerge` only). The patch can therefore set `libraries` (an array of `{id, path, ...}`, replaced wholesale) and `capture.outputDir`. Two handlers then use those values as the argument of `shell.openPath`, which on Windows performs a ShellExecute open on whatever the path is (a program, script or document, not just a folder):

```ts title=src/main/index.ts startLineNumber=642 endLineNumber=642
  ipcMain.handle('libraries:open', (_e, id: string) => { const l = (settings.get().libraries ?? []).find((x) => x.id === id); if (l) void shell.openPath(l.path) })
```

```ts title=src/main/index.ts startLineNumber=659 endLineNumber=659
  ipcMain.handle('library:openFolder', () => shell.openPath(settings.get().capture.outputDir))
```

`LibrarySources.add` validates folders, but only on the `libraries:addFolder` path that goes through a native dialog; the settings channel bypasses it. Neither handler checks that the target is a directory. The renderer's own code never writes `libraries` through `settings:set`, so the legitimate flow does not depend on this.

A related weaker case: `ownCloud:set` accepts any `folder` string, and `ownCloud:open` creates it recursively and opens `<folder>/Clutch`, which allows creating directories and opening Explorer at attacker-chosen (including UNC) locations, but cannot launch a file because `Clutch` is appended.

## Proof of Concept

1. Start the real src/main/index.ts with the electron module stubbed so the actual ipcMain handlers register, and shell.openPath records its argument.
2. As a compromised renderer would, call settings:set with libraries containing an entry whose path is an existing executable, then call libraries:open with that entry id.
3. Call settings:set with capture.outputDir set to another executable path, then call library:openFolder.
4. Read the recorded shell.openPath calls: both attacker-chosen executable paths were passed to the shell.
5. Apply the fix (directory check) and repeat: no call is made for the executable paths, while a real directory still opens.

```js
// poc_open.cjs - stub.cjs stubs 'electron' and records shell.openPath calls
require('./stub.cjs')
process.env.CLUTCH_NO_UPDATES = '1'
require('tsx/cjs'); require('./src/main/index.ts')
const H = (c, ...a) => globalThis.__handlers.get(c)({}, ...a)
;(async () => {
  await new Promise(r => setTimeout(r, 3000))
  // an existing executable stands in for C:\Windows\System32\cmd.exe or \\attacker\share\payload.exe
  await H('settings:set', { libraries: [{ id: 'x', name: 'x', path: '/bin/sh', kind: 'folder', addedAt: '' }] })
  await H('libraries:open', 'x')
  await H('settings:set', { capture: { outputDir: '/bin/ls' } })
  await H('library:openFolder')
  console.log('shell.openPath calls:', JSON.stringify(globalThis.__calls))
  process.exit(0)
})()
```

## Code Analysis

**Location 1:** `src/main/index.ts` (line 642)
  Sink: library path from settings opened with shell.openPath

  **Suggested Fix:**
```diff
-   ipcMain.handle('libraries:open', (_e, id: string) => { const l = (settings.get().libraries ?? []).find((x) => x.id === id); if (l) void shell.openPath(l.path) })
+   ipcMain.handle('libraries:open', (_e, id: string) => { const l = (settings.get().libraries ?? []).find((x) => x.id === id); if (l && isDirectory(l.path)) void shell.openPath(l.path) })
```

**Location 2:** `src/main/index.ts` (line 659)
  Sink: clips folder from settings opened with shell.openPath

  **Suggested Fix:**
```diff
-   ipcMain.handle('library:openFolder', () => shell.openPath(settings.get().capture.outputDir))
+   ipcMain.handle('library:openFolder', () => { const dir = settings.get().capture.outputDir; return isDirectory(dir) ? shell.openPath(dir) : '' })
```

**Location 3:** `src/main/index.ts` (line 60)
  Add directory-check helper used by both handlers

  **Suggested Fix:**
```diff
- const TITLEBAR = { color: '#00000000', symbolColor: '#c3c5cc', height: 44 }
+ const isDirectory = (p: string) => { try { return fs.statSync(p).isDirectory() } catch { return false } }
+ const TITLEBAR = { color: '#00000000', symbolColor: '#c3c5cc', height: 44 }
```

**Location 4:** `src/main/index.ts` (line 440)
  Entry point: renderer patch merged into settings without validation

  **Suggested Fix:**
```diff
-   ipcMain.handle('settings:set', (_e, patch: Partial<Settings>) => settings.set(patch))
+   ipcMain.handle('settings:set', (_e, patch: Partial<Settings>) => { const { libraries: _mainOnly, ...rest } = (patch ?? {}) as Partial<Settings>; return settings.set(rest) })
```

## Remediation

Make the main process the only writer of path-valued settings. Strip `libraries` (and other main-managed fields) from patches received on `settings:set`, and accept `capture.outputDir` and `ownCloud.folder` only when they equal a folder the user just chose through the native folder dialog. Independently, make every `shell.openPath` call defensive: open only paths that exist and are directories, and refuse files and anything with an executable or script extension. Apply the same directory check to `ownCloud:open`.

## Fix Verification

Gate 1: edits are single-line replacements plus one added helper line; fs is already imported in index.ts. Not type-checked in the repository checkout (no node_modules there); the first two edits and the helper were applied to a copy and executed under tsx. Gate 2: re-running the PoC against the patched copy produced no shell.openPath call for the executable paths. Gate 3: a real directory configured as a library still reached shell.openPath; library:openFolder returns an empty string (the normal success value of openPath) when the folder is missing. Gate 4: the settings:set change that strips libraries was not run (gap); the renderer never sends libraries through settings:set (sources.add and remove call SettingsStore.set inside the main process), so the Settings UI should be unaffected, but this was reviewed statically only. Gate 5: no repository test covers these handlers (gap); validating outputDir and ownCloud.folder as described in the remediation is not included in the patch and still needs a design decision.

## Assumptions

The attacker can run script in a Clutch renderer or otherwise call the preload API (for example through an XSS in clip titles, game names or server-supplied data). On Windows, `shell.openPath` on a file executes it via its registered handler; a Windows security prompt may appear for files from network locations. The harness runs on Linux with Electron stubbed, so the actual launch on Windows was not observed.
