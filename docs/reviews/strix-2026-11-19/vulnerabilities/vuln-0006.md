# PowerShell command injection via audio-source process name lets a compromised renderer run arbitrary commands in the main process

**ID:** vuln-0006
**Severity:** HIGH
**Found:** 2026-11-19 17:04:32 UTC
**Target:** Clutch desktop app (Electron main process)
**CWE:** CWE-78
**CVSS:** 7.8
**Confidence:** High
**Fix Effort:** Trivial

## Description

The app-audio feature builds a PowerShell `-Command` string from `capture.audioSources[].process` and only doubles single quotes, but the value sits inside a PowerShell double-quoted string, where `$(...)` and `"` are still interpreted. Any script that can call `window.cf.settings.set` (the renderer, which the project treats as untrusted) can store a crafted process name and obtain arbitrary command execution as the logged-in user outside the renderer sandbox.

## Evidence

```
stored process value: $(Set-Content -Path /tmp/poc_407e_marker2 -Value "rce-from-settings")
marker: rce-from-settings
```
A direct call with the same value also produced `marker exists: true executed as pentester` (command output of `whoami` interpolated by the payload), while the benign value `discord` produced `marker exists: false`. With the allow-list fix applied, the malicious value returned `null` and `marker exists: false`.

## Impact

Escape from the sandboxed renderer to arbitrary OS command execution as the Windows user running Clutch. Demonstrated by writing a file from the injected sub-expression. Reaching this requires script execution in the renderer (for example via an XSS or a malicious renderer-side dependency); no such XSS sink was found in this review, so this is a privilege-boundary break rather than an independently remotely reachable bug. The same sink is also reached if the user selects an app whose process name contains PowerShell metacharacters (`$`, `(`, `)`, `;`, backtick are all legal in Windows file names).

## Counterevidence

No validation exists on `settings:set` or in `AppAudioSource`; only a trailing `.exe` strip and single-quote doubling, which do not neutralize `$(...)`. Counter-considerations: exploitation needs renderer script execution, and the renderer has a strict CSP (`script-src 'self' blob:`), React with no `dangerouslySetInnerHTML`/innerHTML sinks was found, so a renderer foothold is not currently demonstrated. Verified the injection only with `pwsh` on Linux, not Windows PowerShell 5.1, but `$(...)` expansion inside double-quoted strings behaves identically in both.

## What Would Change This Severity

Finding a reachable XSS or other renderer-script-execution bug (or a remotely controllable source of process names/settings) would raise this to critical; proof that the renderer can never run attacker-chosen script would lower it to low (hardening).

## Technical Analysis

`findAppRootPid` in `src/main/capture/appAudio.ts` interpolates the process name into a script passed to `powershell.exe -Command`:

```ts title=appAudio.ts startLineNumber=12 endLineNumber=16
export function findAppRootPid(processName: string): Promise<number | null> {
  const exe = `${processName.replace(/\.exe$/i, '')}.exe`
  const script = `Get-CimInstance Win32_Process -Filter "Name='${exe.replace(/'/g, "''")}'" | ForEach-Object { "{0} {1}" -f $_.ProcessId, $_.ParentProcessId }`
  return new Promise((resolve) => {
    execFile(POWERSHELL, ['-NoProfile', '-NonInteractive', '-Command', script], ...
```

The `-Filter` argument is a PowerShell double-quoted string, so the `'`-doubling provides no protection: `$(...)` sub-expressions and a literal `"` are evaluated/terminate the string.

Data flow: renderer `window.cf.settings.set(patch)` -> `ipcMain.handle('settings:set')` (`src/main/index.ts`) -> `SettingsStore.set` -> `deepMerge` (arrays and strings are copied verbatim, no schema validation) -> persisted in `settings.json`. When the replay buffer starts (`buffer:start` IPC, game detection, or start-on-launch), `replayBuffer.ts` creates `new AppAudioSource(src.id, src.process!)` for every enabled `kind: 'app'` source, and `AppAudioSource.start()` -> `attach()` -> `findAppRootPid(this.processName)` runs the script, and repeats every 10 s while the app is not found. The injected code runs in the PowerShell child spawned by the privileged main process, with the user's full rights. The sibling helper `getWindowRect` in `foreground.ts` strips everything outside `[\w.\- ]` before building its script, which shows the intended pattern was not applied here.

## Proof of Concept

1. In a Linux test harness, stub the `electron` module and point the hard-coded Windows PowerShell path at `pwsh` (the injected sub-expression is evaluated by PowerShell the same way on Windows).
2. Instantiate the real `SettingsStore` and apply the patch a compromised renderer would send through `settings:set`: an audio source of kind `app` whose `process` value is a PowerShell sub-expression that writes a marker file.
3. Confirm the malicious value is stored unchanged, then call the real `findAppRootPid` with it, exactly as `AppAudioSource.attach()` does.
4. Observe the marker file is created by the sub-expression. A control run with `discord` creates nothing, and the patched function (allow-list check) returns null without executing the payload.

## Remediation

Validate the process name against an allow-list of file-name characters before using it, and reject anything else; do not rely on quote doubling inside a double-quoted PowerShell string. Preferably pass the name to PowerShell as data (environment variable or script parameter) instead of building code from it. Additionally validate `capture.audioSources[].process` (and other free-text fields) in the `settings:set` handler so a renderer cannot persist values the main process later treats as code.

## Fix Verification

Gate 1: fix_before copied verbatim from lines 12-14 of src/main/capture/appAudio.ts; syntax exercised by running the patched function under tsx. Gate 2: re-ran the original payload against the patched function: returned null, no marker file created. Gate 3 (bypass): the allow-list excludes `$`, backtick, `"`, `'`, `;`, `(`, `)` so no PowerShell expansion or string termination is possible inside the double-quoted -Filter value; `getWindowRect` in foreground.ts already uses the same character class. Gate 4: ordinary names like `discord`, `Battle.net`, `Game Name.exe` match the pattern and behave as before (control `discord` run returned null only because no such process exists on the Linux harness). Gaps: not run on Windows, no repository test suite or lint run.

## Assumptions

Attacker already has JavaScript execution in the Clutch renderer (or can make the user select an app with a malicious process name). Windows target; Linux reproduction used `pwsh` to evaluate the same script text. `settings:set` performs no validation of audio-source fields.
